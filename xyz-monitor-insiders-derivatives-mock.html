The derivative half of a Form 4

The Insiders tab reads Table I only — actual share transactions. Table II, the derivative half, is counted per filing and shown as a +4D marker with a tooltip explaining why it is not in the table: a derivative row's “price” is a strike, and letting a strike into the PRICE column would put two different quantities in one place. That reasoning is still right. What it got wrong is concluding that the answer was to leave the data out — because the missing half is what tells you whether a sale was a decision or a payday. Below: what including it costs, in three shapes.

The case, in one row. The screenshot that started this: ARM · Haas Rene · CEO · sell 5,191 @ $258.66 — which reads as a CEO taking $1.34M off the table. Table II of the same filing says those 5,191 shares did not exist that morning: they were created by exercising options struck at $12.04, minutes earlier. Same filing, same day. One of those is a view on the price. The other is compensation being converted to cash, on a schedule set years ago. The table as shipped cannot tell them apart.

01Kind column + strike of its ownrecommend · the base

Derivative rows join the table as rows. KIND says which SEC table each came from, STRIKE and EXPIRY are columns only Table II fills, and PRICE stays what it has always been — the price of a share transaction. No column ever holds two quantities. Everything stays sortable and filterable across the whole set, which the alternatives below give up. Derivative rows carry a faint tint so that a sort by VALUE, which interleaves the two kinds, does not require reading the KIND chip on every line.

STRIKE is the exercise price written on the form, never a transaction price · EXPIRY turns amber inside 90 days, because an option exercised weeks before it lapses is mechanical, not a view · a derivative row has no VALUE: shares × strike is a number nobody paid and nobody received, so the column stays empty rather than inventing one.
forOne table, one mental model. Every column still holds exactly one quantity. Sort, filter, search and the pager keep working across the whole set — a “show me every option exercise over $5M this quarter” is the same machinery as everything else, with no new query path.
againstTwo more columns that are blank on most rows, and the default view gets noisier: option grants and exercises outnumber open-market buys heavily. Mitigated by the KIND chips defaulting to shares — the tab opens exactly as it does today and derivatives are one click away.

02The exercise-and-sell pairrecommend · on top of 01

The pattern worth naming. An M on Table II and an S on Table I, same filing, same date, matching share counts, is a cashless exercise: the insider created shares at the strike and sold them the same day. The legs stay separate rows — sortable, filterable, individually true — and the pair is a brace drawn across them with the arithmetic stated. It is marked INFERRED because it is: the form states two legs and says nothing about their relationship. Where the counts do not match exactly, or a partial sale spans two filings, no brace is drawn rather than a fuzzy one.

forThis is the actual insight, and it is unreachable without Table II. It changes the reading of the single most common large row on the tab — a big CEO sale — from “conviction” to “compensation”, or confirms it is neither.
againstA derivation, in a lane whose whole footer promises nothing is derived. Survivable only if it is marked, if the legs stay independently visible, and if the matcher declines to guess: exact filing, exact date, exact count, or no brace.

03Expand-in-place under the markernot recommended

The +4D marker becomes a control: click it and the filing's derivative legs unfold beneath the share row. The default table is untouched — which is the appeal, and also the problem.

forZero cost to the default view; no new columns; the disclosure that already exists becomes the affordance, which is tidy.
againstDerivatives stay invisible to sort, filter, search and the pager — “every option exercise over $5M” is unanswerable, because the rows are not in the result set, they are a detail of rows that are. That is a second, weaker class of data in one table, which is the thing this tab was built to avoid. It also hides the pattern in 02 behind a click per row, when the pattern is the point.

·What it costs

Parser. parseForm4 already walks derivativeTransaction blocks to count them; it would read their fields instead of discarding them — conversion-or-exercise price, expiration date, underlying title and amount. Same shapes as Table I, same null-honesty rules: a footnoted strike is absent, never zero.
Store. Three columns on tx (strike, expiry, under) plus a kind flag, all nullable, added by the same ALTER-that-may-fail migration the congress lane uses. No new table: a derivative transaction is a transaction, and splitting them would mean two queries behind one pager.
Feed. One value in the existing codes whitelist and a kind filter in the shared WHERE builder — the pager keeps counting the set the rows come from.
Client. Three columns in INS_COLS (hidden by default, reorderable like the rest) and the KIND chips. The pair brace in 02 is a render-time pass over the loaded page, not a stored relationship — nothing about it is persisted, so it can be wrong without corrupting anything.
Backfill. Nothing. The documents are already fetched and already parsed; the derivative half is being thrown away at the last step. Re-reading the stored filings is a insiders requeue all.
