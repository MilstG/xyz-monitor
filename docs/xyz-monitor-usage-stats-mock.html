Usage: who uses the site, and how

A new Usage fold in the Admin tab. Today the only usage signal is user.lastSeen, and it only moves on DM, alert, push and AI calls, so someone who reads the Markets table all day looks inactive. The fold adds a small first-party beacon that records which tab is on screen and for how long, plus counts of a short, fixed list of actions. It rolls that up into daily aggregates and shows the operator reach, time spent, adoption and retention. Following the site's existing rule for operator power, members are told, can see their own numbers, and every per-member drill-in is audited.

3 · How it is measured — the data model is deliberately smaller than the question.

The beacon: visible time per tab, nothing else

The client keeps an accumulator {tab → visible ms}. It ticks only while document.visibilityState==='visible' and there was input in the last 5 minutes, so an idle wall monitor doesn't count as 8 hours. It flushes with navigator.sendBeacon('/api/usage') every 60s and on pagehide. The hook point is showView (public/js/backtest.js), which every tab switch already goes through.

Actions are a fixed allowlist of counters, call · target · alert · share · csv · ask · ai-report · drawer-open · telegram-link · push-enable, incremented where each feature already lives: server-side at the authenticated call wherever there is one, and on the beacon only for the two browser-only actions (CSV export, drawer open), clamped to 50 per beacon. No free text, no tickers, no filter state.

Storage: daily aggregates, not an event log

One table in src/accounts.js:

usage_day(day, uid, kind, key, n, ms), primary key (day, uid, kind, key), where kind is tab | dev | act | hr | perf | err | wk. hr is the weekday × hour (ET) bucket for the heatmap; wk is a yes/no weekly-active bit per member, the one kind exempt from the 30-day fold (kept 8 weeks plus the week in progress, the owner's minimal-retention call) so join-week retention can reach past the window. Error text lives in a small usage_err table, capped at 200 distinct errors per build (500 overall, 20 new per member per day, and only for builds the deployment served), messages stored with quoted text removed. The server upserts in memory and flushes every 60s. At about 30 members × 25 tabs × 30 days that is roughly 23k rows, which is trivial for SQLite.

After the retention window (30 days, the owner's decision) rows fold into uid=0 sitewide totals, so the long-run tab trend survives and the per-person history does not.

Public visitors

Signed-out viewers get a random id in localStorage (uid=-1 bucket, id hashed server-side with a daily salt). That is enough for "distinct visitors per day" without IPs, fingerprinting or cookies that follow anyone off-site. It is off by default behind the + public toggle's server flag. Decided: off. Build A ships the flag (USAGE_PUBLIC) but not the visitor id; signed-out beacons are acknowledged and dropped. Build C kept it that way: the id path is deliberately not built.

What the numbers mean

  • Active: at least 60s of visible time that day (ET day, to match the rest of the site).
  • Stickiness: mean daily active ÷ distinct active in the range.
  • Reach: share of active members who opened the tab.
  • Device: coarse class from the UA plus a PWA flag (display-mode: standalone), never the raw UA.
  • Online now: already known server-side (dmOnline() / SSE), so it's free.

Client health rides the same pipe

The beacon also carries perf (time from navigation to the first table paint, once per page load) and deduped onerror/unhandledrejection messages (cut to 200 characters) with file:line, keyed by build, plus the build the tab runs, for the stale-build count. That turns "works on my machine" into a panel. The lazy-module and 409 stale-build work from builds -103 and -108 becomes measurable instead of assumed.

Cost and the event loop

With about 20 concurrent members at one beacon a minute, that's one small POST per 3s. Handling is an in-memory map increment, and the flush is one prepared-statement upsert batch inside a transaction every 60s. Reads are served through sendCachedBody keyed on the flush generation, like every other admin payload. No new dependencies.

4 · Privacy: the same rule as the read-through — operator power is disclosed and audited (README: "a record of when they did is what keeps it accountable rather than silent").

Disclosed

A line in the member guide, in Account ("Your usage"), and once as a dismissible notice after the deploy. The Account card shows the member exactly the summary the operator sees about them.

Audited

The sitewide panels (KPIs, tabs, adoption, cohorts, heatmap) are aggregates and aren't logged. Opening one member's drill-in writes dm_audit(action='view-usage', detail=handle), which shows in the same read log as the message read-through.

Not collected, by design

Search text, filters, column layouts, which tickers someone looks at, and anything typed. Per-ticker interest is useful, but it is also what a member would least expect the operator to watch. If wanted, it goes in only as sitewide counts with no uid (see open questions).

5 · Decisions — the owner's answers (after build -108), built into stage A (build 2026.09.24-109) and kept through B + C (build 2026.09.24-110).

Per-member detail, or aggregates only?

Decided: per-member, audited. The alternative is aggregates only, with no member table. That's more private, but you lose "who stopped coming", which is most of the value in a small invite-only group.

Can members pause it?

Decided: yes, visible as "paused". This costs some completeness but keeps trust, and it matches the Messages disclosure tone. The alternative is disclosure only, with no opt-out.

Track public (signed-out) visitors?

Decided: off. Turn it on if public reach matters for deciding which features to un-gate. It needs a daily-salted anonymous id and no IP storage.

Sitewide ticker interest?

Decided: no. Had it been yes: drawer opens per ticker counted with no uid, which gives a "most looked-at names" list for the Focus and Earnings desks.

Retention window

Decided: 30 days per member, then only anonymous sitewide totals remain. 30 days is enough for "who's active"; the range toggle stops at 30d, and per-member "vs prior" is blank at 30d (the prior month is already folded). Longer cohorts run on the sitewide totals only.

6 · Build plan — three builds, each shippable. All three are built.

Build A · beacon + core panel

Built in build 2026.09.24-109. usage_day table and migration, POST /api/usage (sendBeacon, same-origin, size-capped, one per 30s per uid), in-memory accumulate plus a 60s flush, GET /api/admin/usage?r=, the KPI strip, the daily active chart, the tabs table, the members table, the Account "Your usage" card (in the Messages rail: the terminal has no separate Account page), the pause toggle, the 30-day retention fold, and the disclosure. Tests: accumulator visibility and idle rules, the upsert rollup, admin-only route, and the audit write on drill-in.

Build B · adoption, cohorts, heatmap

Built in build 2026.09.24-110. Action counters at the existing call sites (a stamped call or target in accounts.send, alert create from a chat or the panel, share, ask, AI report, Telegram link, push), CSV and drawer-open on the beacon; the adoption funnel; join-week cohorts (from user.createdAt, read off the weekly wk bit so they reach past the 30-day window); the weekday × hour heatmap in ET; the drill-in's features row.

Build C · client health

Built in build 2026.09.24-110. Perf and error fields on the beacon, deduped by message + file:line and keyed by build; the health cards (first paint p50/p75 against the previous build, distinct errors and hits with the top error's member count, stale builds); and a "quiet tab" flag in Feature visibility. Public visitors and sitewide ticker interest were decided off and are not built.
