The same grid, read in the unit the rest of the app speaks

The heatmap shows the funding a 1× long paid per bucket — an honest cost, but a unit nothing else on the site uses. The Markets table, the terminal, the carry column and the drawer all quote funding as an annualized rate (hourly × 24 × 365). So a row reading +0.031% per 24h has to be converted in your head before it means anything, and the three timeframes each print a different number for the same market. This adds a read as switch — annualized or per bucket — with annualized as the default. Same cells, same colour semantic, same server payload; the timeframe becomes a resolution rather than a quantity, and one market reads one number at every zoom.

2 · One market, three resolutions, one number  what annualizing buys

SMCI, the same day, read off all three grids. Per bucket the three rows disagree by design — 8×, then 3×. Annualized they agree, and the buttons become a smoothing choice.

◆ per bucket — three quantities, three caps
◆ annualized — one quantity, one cap

Annualizing is a multiplier, not a new measurement. A cell is the mean hourly rate the spine saw in that bucket, scaled out to the bucket's width; annualized it is that same mean scaled out to 8 760 hours instead. So an 8h cell is multiplied by 1 095, a 24h cell by 365, a 1h cell by 8 760 — and a day that cost +0.031% to hold reads +11.4% at every resolution, because it is the same payments piled differently. This is exactly the convention the Markets table already prints in its funding column (hourly × 24 × 365), which means the newest 1h cell of a row and the table's number for that ticker are, for the first time, the same number.

3 · One cap across resolutions  a zoom that repaints is not a zoom

Eight rows at 24h, annualized, drawn two ways. Left: the proposal — every resolution shares the 8h grid's annualized cap. Right: each resolution keeps its own percentile, so the same day changes colour when you change the button.

resolution
◆ proposed — shared cap, colours hold across 1h / 8h / 24h
◆ alternative — per-resolution cap, colours move with the button

Per bucket, each timeframe needs its own cap — the shipped grid does that, because the 8h quantity is genuinely eight times the 1h one. Annualized, they are one quantity, and what differs between resolutions is only how it is sampled: the three grids cover different windows (2, 14 and 30 days) at different smoothing, so each one's own 98th percentile lands somewhere else. Keep three caps and a cell that reads +40% APR is faint on one button and saturated on the next — the same rate, two hues, chosen by a control that is supposed to be a zoom. So annualized mode uses one cap for all three resolutions: the default (8h) grid's own annualized percentile, shipped by the server as today and multiplied client-side. Hourly spikes saturate more often under it, which is what a cap is for; the colour of a rate never depends on how finely you sliced it.

4 · The numbers at the precision an annual rate deserves

The decimal count follows the unit, not the timeframe. Per bucket, the mean column derives one shared decimal count from the grid's cap so a 1h grid is not forced into a 24h grid's decimals — three significant figures at the cap, which is what separates one row's carry from the next at 0.010%. Annualized the cap sits near tens of percent, and the same rule would print +11.412% — false precision on a number whose inputs are hourly prints rounded to the basis point. So annualized prints one decimal when the cap is above 10% and two below it, capped at two. The ≈0% rule carries over unchanged: a mean that rounds away at the grid's precision wears neither colour and claims no sign.

5 · What this pins down

Client-only — the payload does not change

/api/funding already ships per-bucket cells, one cap per timeframe and each axis's bucketHours. Annualized is cell × 8760 / bucketHours applied at render time, and the shared cap is axis['8h'].cap × 1095. No new field, no ETag change, no rebuild; the board's 60s TTL and 304 discipline are untouched.

The alternative — shipping an annualized grid beside the per-bucket one — doubles a ~60×120 payload to carry a multiplication.

Annualized is the default

It is the unit every other funding readout on the site uses, so a reader arriving from the Markets table meets a familiar number. Per bucket stays one click away because it answers a different question — what did the last day actually cost — that a rate does not.

The choice is remembered per browser in localStorage, the same way the dim-off switch is; a bare #funding deep link opens whatever was chosen last, annualized on a fresh browser.

Every tooltip carries both

Annualized, a cell reads +41.2% APR — longs pay · +0.0376% over this 8h bucket; per bucket, the same cell leads with the bucket cost and trails the APR. The rate says how crowded, the bucket says what it cost; a reader sizing a hold wants the second even while scanning by the first.

Sorts are unit-blind, colours are not

Longs pay most, strongest carry and the rest rank by the row mean, and a positive multiplier preserves every ranking — flipping the unit never reorders rows. Colours are re-derived, because the cap moves with the unit, but under annualized they are then stable across the three resolutions (§3).

The timeframe label changes with the unit

Per bucket the control reads funding per, because that is what the buttons choose. Annualized it reads resolution, because that is now what they choose. The caption, the legend's trailing per 8h / APR tag and the axis footer follow the same rule; the tab title and status line do not move.

Coverage rules are unchanged

A bucket under half coverage is still null and still hatched; multiplying an unknown by 1 095 does not make it a number. The newest column stays the last complete bucket for the same reason it does today.

6 · Still open

Whether the unit belongs in the URL

A #funding link that also carried the unit would make a screenshot reproducible for whoever it was sent to. Not in this proposal — the hash currently carries the tab and the ticker, and the unit is a preference, like the sort. Easy to add if it turns out people share annualized grids and get per-bucket ones back.

Whether the shared cap should be the 8h grid's

The default resolution's percentile is the least surprising anchor: it is what the tab opens on. The 24h grid's would make daily reads fill the palette and hourly reads saturate hard; the 1h grid's would leave daily reads faint. Either is one constant away.
