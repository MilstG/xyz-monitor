Design mock · messages × screener

Share to chat: any cell, any row, any screen, one card

Today a number leaves the screener by being retyped, screenshotted, or re-run as a command in the composer. The proposal: one share glyph that appears wherever data is drawn, one sheet that shows exactly what the room will see, and one message kind — a data card that keeps the app's own formatting, says when it was captured, drifts against the live mark, and opens the same view when clicked. It rides the existing stamp, pin, reply, note-promotion and Telegram-mirror paths untouched.

◆ mock · synthetic prices and conversations, nothing is wired to live data

1 · The affordance  the markets table — nothing at rest, three grains on hover

Hover a row: ⤴ appears after the star (the whole row) · hover a cell: a corner ⤴ on that field alone · tick rows for a screen · right-click for the menu · with a row focused, s shares it.

Why three grains, not one. A cell is a claim ("HOOD funding is +41% — shorts are crowded"); a row is a card ("here's NVDA right now"); a screen is a list ("these five are the setups"). Each has a different shape in the conversation, so the glyph asks which one you meant instead of guessing from where your mouse was. The right-click menu names all three with the exact thing under the cursor, which is also the keyboard path.

What a card carries. A header that says the ticker, the grain and the capture time; a body in the exact shape of the thing shared (one big number, a key/value grid, a table, a list); a footer with the link and the live drift. A card that names a ticker is also a stamp, so it enters the calls record like any $HOOD message — the "quote as a call" box in the sheet is that switch. The note under it is an ordinary message body: searchable, editable, quotable.

One rule. Anything drawn from a state row through a column definition or a section renderer has an address — view, scope, timeframe, coin, keys — and anything with an address can be captured. The glyph sits in the section's own header, where the tooltip and the timeframe segment already live, so no surface grows a new toolbar.

6 · What this pins down
// one message kind. `card` is JSON on the row (dm_msg.card TEXT, validated ≤ 8 KB,
// ≤ 25 rows × 12 keys); `body` keeps the text rendering for search, export and the mirror.
{ v: 1,
  kind: "cell" | "row" | "screen" | "panel" | "chart",
  view: "markets", scope: "stocks", tf: "1d", lens: "names",      // the address
  coin: "xyz:HOOD", keys: ["px","d1","funding","rvol","oi","vsma200"],
  rows: [{ coin, vals: [113.90, 3.1, 0.000047, 2.8, 38.1e6, 12.4] }],   // RAW, never formatted
  filters: { rvol: [">", 2], funding: [">", 20] }, sort: ["funding","desc"],
  at: 1790000000000, px: 113.90,                              // the stamp
  panel: null | { name: "levels", lines: [...] } }                  // drawer sections, signals
  • The serializer is the column table. COL_BY_KEY[k] already owns a label, a getter and a formatter for every screener column; a capture reads the getter, a card renders through the formatter. A column added to the screener is shareable the day it lands, with no second list to forget.
  • Raw values, formatted at read. The card stores numbers, never strings, so the reader's own unit and colour rules apply — and "now" can be computed by running the same getter against the live row. A formatted string could not drift.
  • The stamp is the existing stamp. A card with a coin sets ref/refPx exactly as $HOOD in a body does today; the calls record, the → note promotion and the delete-proof rule all apply unchanged. The sheet's "quote as a call" box is the only new choice, and it defaults on.
  • The link is a hash route. #markets?u=stocks&tf=1d&coin=HOOD&cols=…&f=rvol>2,funding>20 — the app already routes views by hash; this adds the view's own state to it, which the URL bar then gains for free.
  • Telegram and export render body. The text renderer produces the monospace block once, at send, so the mirror, the digest and the JSON export need no card knowledge.
  • Boards are desk-public. A card into a topic board is visible to anyone who joins it — same as a message. Nothing in a card is data a member could not already see on their own screen, since the audience gate is the view gate.
7 · What is missing before this ships
  • Default grain on a plain click. The mock shows both glyphs; on a phone there is no hover. Long-press on a row could open the menu, or the drawer header's ⤴ could be the only mobile path. Undecided.
  • How live is "now". The footer recomputes from the live row on every render, which is free for a cell and a row; for a screen it re-runs the filters over the roster ("3 of 3 still pass"). Cap at, say, 25 rows, or make it a click.
  • Edits. A card is immutable (like a command result); the note under it edits like any message. Re-capture posts a new card rather than mutating the old one, so the record is a sequence of claims, not a rewritten one.
  • Charts. The PNG path exists for /ratio; candles and the correlation matrix would need the same offscreen rasteriser. Not in the first cut.
  • Retention. Cards ride message retention (30d DM, 7d group, pinned exempt). A pinned screen card is effectively a saved screen — which might be a feature.
  • The composer path. A typed /share HOOD funding and /share screen would give the keyboard and the phone the same reach; it is the /alert pattern and costs little once the serializer exists.
