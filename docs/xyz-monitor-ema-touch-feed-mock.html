Design mock · proposal

EMA touch feed: 50 / 200 on H4 and D1, plus what's about to touch

A tab that answers two questions: which names are touching their 50 or 200 EMA right now, and which are about to. Most of the machinery already exists. The ma200 alert lane (src/poller.js ma200Scan, build -32) already reads H4 and D1 EMA200 over closed bars, fires reclaim / breakdown / retest, and dedupes on the firing bar's timestamp. It pushes to the bell and Telegram, but it only speaks after the close, has no EMA50, and has no proximity view. This mock adds those three and gives them a tab.

Cooldown: once per candle is necessary but not enough · what the re-arm rule adds

fires a card touch folded into the open card (no ping) episode re-armed near band

Candles 3–5 chop through the line. "1 per candle" fires three times; that is one fight, not three signals. With re-arm, a new card needs a close outside the re-arm distance first (candle 6). The retouches in 4 and 5 land on the open card as "+2 retouches". Candle 8 is a fresh approach from clear air, so it fires. Candle 9 closes through, which resolves candle 8's card (closed through → breakdown) instead of opening a new one. This is the same clear-air arm the ma200 retest detector already uses (prior close ≥0.25σ clear and didn't touch), applied as persistent state so it also covers the intrabar touch.

Recommended defaults · the parts I'd ship as-is, and why

σ, not flat %, for "near"

1% is a normal hour on HYPE and a big week on GOLD. A flat % band would keep the high-vol names permanently on deck and never show the quiet ones. Distance in the rung's own bar σ (retStd over the last 90 bars, exactly what ma200Scan computes as sdTf) means "0.5σ" is equally close on every name. The % stays on screen next to it, and the % presets remain as a switch.

Tab shows intrabar, phone shows closes

The feed shows touches live, because watching a name tag the 200 is the point of the tab. By default a phone push fires only on the resolution (held / closed through), since that is the confirmed event the -25 rule is built on and the ma200 lane already does it. Intrabar pushes are an opt-in per rung. D1 touches are rare enough to be worth a ping; H4-50 touches are not.

One card per episode, resolved in place

A touch opens a card, retouches fold into it, and the close resolves it. This keeps the feed at roughly one line per real event. It also carries the existing seenAt disclosure: a confirmed ma200 event can say "first seen intrabar 14:20, confirmed at the 16:00 close".

Reuse emaAlertState, add N=50

compute.emaAlertState already takes opts.N. EMA50 is a parameter, not a new detector. The seed cost drops too: 50 needs ~66 closed bars, while the 200 needs 216. EMA50 works on younger listings that the 200 lane is silent on today.

Open questions · your call

1. Does EMA50 get the same four shapes?

The 200's reclaim / breakdown / retest vocabulary has a study behind it (-26) and shadows earning a record (-28). The 50 has neither. Options: (a) touch + near only for the 50, which is informational; (b) the full four shapes, labelled no record yet, with a shadow stream so it earns one. I'd start with (a).

2. D1 for stocks: session bars or 24h?

The Trend board's D1 rung reads session bars for equities (-105: "200-day" = 200 sessions). Using them here keeps the feed consistent with the Trend chart, so the line you see is the line that fires. The cost is that an off-hours touch on the perp doesn't count until the session bar forms. I'd keep session bars.

3. Who sees it?

New tabs usually ship admin-only while they soak (Housing, Liquidity, Backtest). The same here, then open to members once the push volume is known. The KPI strip on the real tab would show the actual 24h counts per policy, which makes that decision easy.

4. Anything beyond 50/200?

If the MA set becomes a user setting (e.g. 21 / 100), the Trend pair board already accepts arbitrary pairs (/api/trend?fast=&slow=). I'd keep this tab fixed at 50/200 so the counts and pushes mean one thing, and leave custom MAs to per-member alert rules.

Build sketch · roughly one build

Server

  1. Generalise ma200Scan → emaScan over N ∈ {50, 200} × {D1, H4}. The N=200 path stays bit-identical; the existing ma200 trigger class keeps its name and payload.
  2. On the mark-extended series maLiveBars already builds: compute gapσ, gap%, a closing/widening flag and the intrabar touch. Keep per-key episode state {armed, openCard, retouches, inZone}, persisted with persistTriggers.
  3. GET /api/ema-feed: {near:[…], cards:[…]} with a ring buffer of ~48h of cards and ETag on the scan version, served via serveCached.
  4. New push class ema (intrabar, opt-in, off by default). Resolutions for N=200 keep riding ma200.

Client

  1. New tab with the two panes above. It polls /api/ema-feed on the snapshot cadence, and 304s when nothing moved.
  2. A row click opens the existing Trend chart modal at that rung (/api/candles?tf=4h|1d already serves the exact bars the EMAs are computed on).
  3. The tab badge counts open (live) touch cards.
  4. Alerts panel: an ema class toggle with per-rung checkboxes.
